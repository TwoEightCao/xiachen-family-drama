# 发布流程（GitHub 发布子代理专用规程）

> 本文件是**发布子代理**的作业手册，也是人工发布的对照表。发布 = **推送 + 从远端复验**，缺一不算完成。

---

## 一、固定信息

| 项 | 值 |
|---|---|
| 仓库根 | `~/.agents/skills/xiachen-family-drama` |
| 远端 | `https://github.com/TwoEightCao/xiachen-family-drama.git` |
| 远端所有者 | `TwoEightCao` |
| 默认分支 | `main` |
| token 文件 | `~/.config/xiachen/gh_token`（权限 600，目录 700，**位于仓库之外**） |
| token 环境变量（备选） | `XIACHEN_GH_TOKEN` |
| 发布器 | `scripts/publish.sh` |

---

## 二、标准发布（一条命令）

```bash
cd ~/.agents/skills/xiachen-family-drama
./scripts/publish.sh -m "fix: 你的改动说明"
```

发布器自动完成：提交本地改动 → 用一次性 URL 推送 → 比对远端 SHA 与本地 HEAD → **从远端重新克隆并跑三个脚本的 `--self-test`**。

其他模式：

```bash
./scripts/publish.sh --dry-run      # 只看会做什么，不推送
./scripts/publish.sh --verify-only  # 不推送，只做远端复验
```

**判据：输出末尾出现 `发布完成：…` 才算成功。** 任一步失败脚本会打印 `FAIL` 并以非 0 退出。

## 三、安全红线（发布子代理必须遵守）

1. **绝不把 token 写进仓库内任何文件** —— 包括 README、脚本、注释、commit message。
   发布器有硬校验：token 文件若在仓库内、或已跟踪文件里出现 token 字面量、或 remote URL 里嵌了 token，**直接拒绝运行**。
2. **绝不回显 token**。所有输出必须经过掩码；不要把 `cat token` 的结果写进对话或日志。
3. **绝不强推**（`--force` / `--force-with-lease` 一律不用）。远端历史只能快进。
4. **绝不把 token 写进 `.git/config`**。推送使用一次性 URL 参数，remote 配置始终保持干净的 HTTPS 地址。
5. **每次发布后必须从远端复验**，不许以「本地 push 成功」当作完成。
6. **不在仓库里执行 `git add -A` 之外的范围操作**；若发现工作区有不该提交的文件（剧本项目、`.env`、密钥），先停下报告。
7. **`DSH_HOME` 永不入库。** 它里面的 `.credentials.yaml`（各 provider 的 key）与 `settings.yaml`（provider / baseURL / 凭据引用名）都是**本机私有配置**，与这个 skill 仓库无关。本仓库是纯文本规格，不携带、不引用、也不应包含任何一方的凭据或中转站信息。
   发布器现在有两道闸门：`.gitignore` 忽略 `*credentials*` / `settings.yaml` / `*.yaml` 等，**且**发布前 `git ls-files` 一旦发现被跟踪的凭据/设置文件就直接拒绝运行（`.gitignore` 只是提示，这道才是闸门）。
   > 为什么这条要写出来：v1.4.1 曾声称 `.gitignore` 做了「纵深防御」，但当时那条规则写的是 `credentials*` —— **它不匹配以点开头的 basename**，而 DSH 用的文件名恰恰是 `.credentials.yaml`。等于那道防线一直是空的。v1.5.1 已修正。

## 四、token 轮换（用户换新 token 时）

```bash
umask 077
printf '%s' '新token' > ~/.config/xiachen/gh_token
chmod 600 ~/.config/xiachen/gh_token
./scripts/publish.sh --verify-only        # 验证新 token 可用
```

轮换不需要改任何代码 —— 发布器只从固定路径读取。

> ⚠️ 若 token 曾出现在对话记录、截图或公共渠道中，**应视为已泄露并立即在
> https://github.com/settings/tokens 吊销**，然后按上面的步骤换成新 token。

## 五、常见故障

| 现象 | 原因 | 处理 |
|---|---|---|
| `FAIL 未找到 token` | token 文件缺失或权限不可读 | 按 §四 写入 |
| `FAIL token 文件位于仓库内` | token 放错位置 | 移到 `~/.config/xiachen/` |
| `FAIL 仓库已跟踪的文件里出现 token 字面量` | 密钥已进版本库 | 立即移除该文件、吊销 token、重写历史后再发布 |
| `FAIL 推送失败（退出码 128）` | token 失效 / 无 repo 权限 / 网络 | 校验 token 是否吊销、scope 是否含 `repo` |
| `FAIL 远端 SHA 与本地 HEAD 不一致` | 推送未生效或被并发推送 | 重新运行发布器；若有他人推送，先 `git pull --rebase` |
| 远端 `--self-test` FAIL | 推上去的版本本身有问题 | 本地修好、重跑三个自检、再发布 |

## 六、发布子代理的调用方式（**可选**，非必需）

父代理或用户可以直接对发布子代理说：

```text
发布：<改动说明>
```

它应当：① 先 `git status --short` 看清改了什么；② 跑 `./scripts/publish.sh -m "<说明>"`；
③ 把**原始输出**（含远端复验结果）回报，不要只回「已发布」。

---

## 七、约定（**仅限本仓库**，不是全局规则）

**本仓库（`xiachen-family-drama`）有改动时，直接发到本仓库即可，不必动用发布子代理。**

一条命令：

```bash
./scripts/publish.sh -m "<改动说明>"
```

- 完成判据：输出出现 **`发布完成：…`**（远端 SHA 与本地 HEAD 一致 + 远端克隆三脚本自检全 PASS）。
- 想更省事也可以直接 `git push`，但**推完要确认远端 SHA 与本地 HEAD 一致** —— 只看到「已推送」不算完成。
- 用 `scripts/publish.sh` 的好处只有两点：不会把 token 落盘到 `.git/config`，且强制做一次远端复验。嫌麻烦可以不用。
- §六 的「发布子代理」是**可选项**，不是必需流程。本约定**不适用于其他仓库**。
